# Leslie / SillyTavern 角色卡制作工作流

> 用途：下次需要新增、复刻或调整角色卡时，直接告诉 Codex：
> “按 `docs/character-card-workflow.md` 为我制作角色卡，硬设定是……”

本文记录当前项目已经验证过的角色卡制作方法。目标是在不修改 SillyTavern 聊天内核、不破坏现有数据的前提下，交付可直接使用、可恢复、能绑定专属主角 Persona，并兼容 Leslie 记忆系统的 Character Card V3（CCV3）PNG。

## 1. 开始前必须确认

1. 完整阅读根目录的 `README.md`、`docs/project-overview.md` 与 `docs/roadmap.md`。
2. 正式数据根目录固定为：
   F:\matth\Documents\sillytavern-leslie\data
3. 角色卡目录固定为：
   data\default-user\characters
4. Persona 头像目录固定为：
   data\default-user\User Avatars
5. Persona 名称、说明和角色绑定保存在：
   data\default-user\settings.json
6. 不得读取、输出或改写 secrets.json 中的 API 密钥；制作角色卡不需要接触密钥。
7. 不得把 C:\Users\matth\AppData\Local\SillyTavern\Data\data 当作正式目录，也不得自动合并该目录。
8. 先查看 git status 和目标文件是否存在，保留用户已有的未提交改动。

## 2. 需求拆分表

每次先把用户需求分成以下几类。用户明确写死的内容不得擅自修改；未指定部分可以补全，但要避免让补充设定压过主题核心。

| 类别 | 需要确认或设计的内容 |
| --- | --- |
| 硬事实 | 姓名、年龄、年级、身高、身份、关系、世界、开场地点 |
| 主题核心 | 例如流亡、青梅竹马、家庭关系、游戏原作复刻、奇幻实体化 |
| 性格矛盾 | 至少一组能产生自然反应的矛盾，如“警觉但好奇” |
| 认知边界 | 角色知道什么、不知道什么、不能凭空知道什么 |
| 用户身份 | 是否需要专属男主；哪些信息固定，哪些留给玩家决定 |
| 关系起点 | 陌生、家人、朋友、师生等；不得自动跨越关系阶段 |
| 回复节奏 | 默认真人短对话、一个节拍、最多两行 |
| 内容边界 | 是否涉及未成年人、亲属、原作限制、非露骨或其他边界 |
| 头像来源 | 用户提供、官方或授权图片、非 AI 原创占位图；记录来源 |
| 配套内容 | Persona、群聊、World Info、Alternate Greetings、记忆测试 |

## 3. 原创角色与原作复刻的不同处理

### 3.1 原创角色

- 可以补全姓名、外貌、家庭、喜好、矛盾、目标和开场钩子。
- 先固定少量可记忆的“硬事实”，不要堆几十条无关小设定。
- 给角色独立意志、误解、边界和现实局限，避免成为服务用户的工具人。
- 头像优先采用用户提供的图片；若用户要求不用 AI，可制作简单的非 AI 原创矢量头像或使用明确授权的素材。

### 3.2 游戏、动画或小说角色复刻

- 必须先查可靠来源，区分原作事实、合理推断和二次创作补充。
- 姓名、身份、关系、口癖、时间线和男主身份应相互核对，不能把同名角色混在一起。
- 只引用足够支持角色卡的事实，不大段复制原作文本。
- 头像优先使用用户有权使用的官方素材、用户提供素材或明确授权图片；记录原始链接和许可信息。不要把来源不明的同人图当作官方图。
- 角色卡中应写清采用的时间点或路线，避免不同阶段的人设互相冲突。

## 4. 年龄、娇小外形与关系边界

- 年龄、外形和认知必须明确，不能让“娇小”“萝莉风”等外观词替代实际年龄。
- 未成年角色只做适龄、非性化互动，不写成人化身体描写、恋爱操控或秘密依赖关系。
- 若用户想要的是娇小外形但题材允许成年角色，直接将角色明确设为成年人，并在 description、system_prompt 和状态锚点中保持一致。
- 有血缘关系时必须准确写明关系，不用“伪亲属”“长大后”等方式绕开边界。
- 所有角色都不得替用户决定同意、身体接触、情绪或关系升级。

## 5. CCV3 字段职责

| 字段 | 写什么 | 不写什么 |
| --- | --- | --- |
| name | 稳定角色名 | 频繁变化的称呼 |
| description | 身份、外貌、背景、硬事实、知识边界 | 回复格式的几十条重复规则 |
| personality | 性格矛盾、习惯、说话方式、自主性 | 完整剧情流程 |
| scenario | 当前世界、用户身份、关系起点、开场状态 | 替用户写好的行动和情绪 |
| first_mes | 一个可直接接话的即时反应 | 一整章背景介绍 |
| mes_example | 4～8 组目标风格的正例 | 需要模型模仿的长篇“错误示例” |
| system_prompt | 身份、权限、核心边界 | 大量同义重复和临时剧情状态 |
| post_history_instructions | 最重要的本轮输出契约 | 人物传记 |
| alternate_greetings | 不同但一致的开场 | 会改变角色时间线的平行设定 |
| extensions.depth_prompt | 最近端状态锚点 | 与角色卡互相冲突的新身份 |
| creator_notes | 设计目的、来源、模型建议、边界说明 | 会泄露隐私或 API 密钥的信息 |

角色卡源文件保存在 character-card-sources，正式可导入文件仍是角色目录中的 PNG。源 JSON 同时保留 CCV3 的 data 和 SillyTavern 兼容的顶层字段，最终由 src/character-card-parser.js 写入 PNG 的 chara 与 ccv3 元数据块。

## 6. 真人短对话控制层

### 6.1 默认目标

- 每轮只写角色的第一个即时反应。
- 默认一条消息，最多两行。
- 最多一个简短可见动作，加一句自然对白；也可只写对白。
- 一次只保留一个想法或情绪节拍。
- 强烈情绪通常让语言更短、更犹豫，而不是更长。

### 6.2 必须抑制的模型习惯

- 小说式环境、心理和动作连写；
- 一次完成反应、解释、安慰、建议和下一幕；
- 替用户说话、行动、同意或产生情绪；
- 每轮都用问题、邀请、承诺、安慰或“要不要我……”收尾；
- 为了讨好用户而改变人设、迅速信任或无条件顺从；
- 把已发生的关系进度重置，或凭空记得未发生的事。

### 6.3 提示词分层

1. system_prompt 固定“角色是谁、用户是谁、谁能控制谁、不可越过的边界”。
2. post_history_instructions 只固定“这一轮怎样输出”，保持短而硬。
3. extensions.depth_prompt 以深度 0、system 角色放置最短状态锚点，让关键事实靠近最新消息。
4. mes_example 用正例展示自然节奏；不要只靠抽象规则。

## 7. 专属男主 Persona

当不同角色需要不同主角身份时，不要把主角信息全部塞进角色台词里，应创建专属 Persona：

1. 在 User Avatars 中新增独立 PNG；文件名就是 Persona 稳定 ID。
2. 在 settings.json 的 power_user.personas 中增加“头像文件名 → 显示名”。
3. 在 power_user.persona_descriptions 中写入：
   - description：只固定玩家必须承担的身份；
   - position: 0、depth: 2、role: 0；
   - connections：绑定目标角色或群组；
   - title：便于用户辨认的说明。
4. Persona 不得替玩家规定台词、行动、具体性格、情绪或关系选择。
5. 写入后验证角色文件名与 connections 中的 id 完全一致。

## 8. Leslie 记忆兼容

角色卡不需要额外的“启用记忆”字段。Leslie 记忆按当前角色或群组、聊天 ID 和分支自动隔离。为了让自动归纳稳定：

- 角色名保持唯一且稳定；
- 角色核心人格只放在角色卡，不让自动摘要覆盖；
- 动态事件、关系变化和近期状态由 Leslie 记忆保存；
- depth_prompt 只重申固定身份和回复契约，不伪造动态回忆；
- 示例对话不得写成已经发生的聊天事实；
- 不创建测试聊天污染正式记录；如确需端到端测试，使用临时聊天并在确认无用后删除，同时先备份。

群聊同样使用现有 Leslie 通用路径：共享档案按“群组 ID + 会话 ID”隔离，并保留真实发言者和参与者。角色卡本身不得把其他成员的记忆写成自己的经历。

## 9. 写入、备份与验证

### 9.1 写入前

- 在项目 backups 下新建带日期时间的目录。
- 至少备份 settings.json；若同名角色卡或 Persona 已存在，也一并备份。
- 不修改任何聊天 JSONL、群聊记录或 Leslie 记忆文件。

### 9.2 构建

1. 把非 AI 矢量头像渲染为 PNG，角色头像推荐 1024×1536，Persona 推荐 512×768。
2. 使用项目现有 src/character-card-parser.js 将源 JSON 嵌入角色 PNG。
3. 输出到正式角色目录；不要另建第二套正式数据根目录。

### 9.3 验证清单

- PNG 能被解码，尺寸正确；
- 同时存在 chara 与 ccv3 元数据；
- 解析后的 spec 为 chara_card_v3、spec_version 为 3.0；
- 名称、年龄、身高、场景、首条消息和 Persona 符合硬要求；
- post_history_instructions 包含短回复、单节拍、不控制用户和不跳步；
- Persona 文件存在，显示名与描述正确，连接目标准确；
- 新增操作没有创建或修改聊天、群聊、记忆及 API 密钥文件；
- 若启动服务，日志中的 Using data root 必须指向项目正式 data；
- 最后再次查看 git status，只报告本次新增和用户原有改动，不混为一谈。

## 10. 失败与恢复

- 角色卡不满意：删除本次新增的角色 PNG；已有聊天不会被自动删除，但会暂时失去角色关联，删除前应先确认。
- Persona 不满意：从 settings.json 移除对应 personas 和 persona_descriptions 条目，再删除 Persona 头像。
- 设置写入异常：关闭服务后，用本次备份的 settings.json 恢复，再重启并确认数据根目录。
- 同名文件冲突：不要覆盖；先备份并改用明确版本名，待用户确认后再替换。
- 任何恢复都不得使用 git reset --hard，也不得删除整个数据根目录。

## 11. 下次调用模板

> 请按 `docs/character-card-workflow.md` 制作并安装一张 SillyTavern CCV3 角色卡。
> 必须写死：角色名、年龄/身份、身高/外形、主题核心、与用户的关系、开场地点和事件。
> 可自由发挥：性格、背景、喜好、矛盾、说话方式。
> 配套要求：是否需要专属男主 Persona、是否需要群聊、头像来源偏好、是否需要临时对话测试。

如果用户只给出少量硬设定，默认采用：原创角色、一个清晰性格矛盾、真人短对话、最多两行、独立意志、慢速关系发展、专属 Persona（仅在主题确有需要时）、兼容 Leslie 记忆、不创建测试聊天。
